# OPERATIONS.md — что делать, когда что-то случилось

DEPLOY.md — как поднять сервер один раз. Этот файл — про жизнь после запуска:
резервные копии, потерянный телефон, кончившееся место, непонятные симптомы.

Все команды выполняются на VPS из папки с `docker-compose.yml`. Если консоль VPS
не открывается, те же действия есть в браузере — **Actions → «Сервер» → Run
workflow** (docs/DEPLOY.md §8b), это работает и с телефона.

Ключевое различие, из которого следует всё остальное:

| | где лежит | что будет, если потерять |
| --- | --- | --- |
| База сервера `data/server.db` | VPS | аккаунты, контакты, недоставленные сообщения, резервные копии |
| Приватные ключи устройства | только телефон | переписку этого человека не расшифровать больше нигде |
| Локальная переписка | только телефон | остаётся то, что попало в резервную копию |

Бэкап сервера **не** возвращает переписку: у сервера её нет в читаемом виде.
Переписку возвращает резервная копия, которую делает сам человек в настройках
приложения (ARCHITECTURE.md §2.7). Это два разных бэкапа, и они не заменяют друг
друга.

---

## 1. Регулярный бэкап базы сервера

### Почему нельзя просто `cp`

База работает в режиме WAL: часть уже принятых сообщений в момент копирования
может лежать не в `server.db`, а в `server.db-wal`. Обычный `cp` под нагрузкой
даёт файл, который откроется, но окажется на несколько минут «в прошлом» — либо
не откроется вовсе. Правильный способ — попросить саму SQLite сделать
согласованную копию:

```bash
docker compose exec server node -e "
  const db = require('better-sqlite3')('/app/data/server.db');
  db.exec(\"VACUUM INTO '/app/data/backup-\" + new Date().toISOString().slice(0,10) + \".db'\");
"
```

`VACUUM INTO` берёт целостный снимок и попутно выбрасывает пустые страницы,
поэтому копия обычно меньше исходной базы. Файл появится в `./data/` рядом с
базой — то есть на том же диске, что и оригинал.

### Копию нужно унести с VPS

Бэкап на том же диске защищает от испорченной базы, но не от потерянного
сервера. Забрать к себе на компьютер:

```bash
scp пользователь@сервер:family-messenger/data/backup-2026-08-03.db ./
```

### Раз в сутки без напоминаний

```bash
crontab -e
```

```
0 4 * * * cd /home/пользователь/family-messenger && docker compose exec -T server node -e "const db=require('better-sqlite3')('/app/data/server.db');db.exec(\"VACUUM INTO '/app/data/backup-\"+new Date().toISOString().slice(0,10)+\".db'\")" && find data -name 'backup-*.db' -mtime +14 -delete
```

`-T` обязателен: без него `docker compose exec` требует терминал, а у cron его
нет, и задание молча падает каждую ночь. `find … -mtime +14 -delete` держит
двухнедельную глубину — иначе копии съедят диск, и вместо защиты бэкап станет
причиной аварии.

Раз в месяц проверяй, что копия открывается. Бэкап, который никогда не
восстанавливали, — это предположение, а не бэкап:

```bash
docker compose exec server node -e "
  const db = require('better-sqlite3')('/app/data/backup-2026-08-03.db');
  console.log(db.prepare('SELECT COUNT(*) n FROM users').get());
  console.log(db.pragma('integrity_check'));
"
```

## 2. Восстановление из копии

```bash
docker compose down
cp data/server.db data/server.db.сломанная           # прежнюю не выбрасываем
cp data/backup-2026-08-03.db data/server.db
rm -f data/server.db-wal data/server.db-shm          # WAL от прежней базы к этой не относится
docker compose up -d
docker compose exec server npm run status
```

Удалить `-wal` и `-shm` обязательно: SQLite приняла бы их за журнал новой базы,
а они от старой — это прямой путь к испорченному файлу.

Что при этом происходит с людьми: телефоны переподключатся сами. Сообщения,
принятые сервером после снятия копии, потеряются — те, что не успели дойти до
получателя. Уже доставленные лежат на телефонах и никуда не деваются. Аккаунты,
контакты и `@теги` вернутся на момент копии, поэтому кто-то может обнаружить, что
недавно добавленный контакт пропал: пусть добавит заново по тегу.

## 3. Потерянный или украденный телефон

Порядок именно такой: сначала отрезать доступ, потом разбираться.

```bash
docker compose exec server node dist/cli/revoke-device.js                              # список устройств
docker compose exec server node dist/cli/revoke-device.js --device=ad4e6bf9-...        # отозвать
docker compose exec server node dist/cli/revoke-device.js --device=ad4e6bf9-... --undo # вернуть
```

То же есть в приложении у главного: настройки → участник → «Отозвать доступ
устройству» (docs/DEPLOY.md §8c).

**Что даёт отзыв.** Телефон немедленно отключается от сервера и больше не
получает новых сообщений и не может их отправлять.

**Чего он не даёт, честно.** Переписка, уже лежащая на том телефоне, остаётся на
нём. Она зашифрована на диске и закрыта кодом приложения, если код был включён,
но отзыв её не стирает и стереть не может — сервер до содержимого телефона не
достаёт. Если код не был включён, а телефон разблокирован, читать её сможет тот,
у кого он в руках. Поэтому код блокировки — не «дополнительная опция», а
единственное, что работает в этом сценарии.

**Дальше — новый телефон.** Человек ставит приложение и **входит по своей почте и
паролю**: аккаунт, `@тег` и контакты остаются его. Вход автоматически отзывает
прежнее устройство и рассылает контактам новые ключи (ARCHITECTURE.md §2.4) —
руками ничего доводить не нужно.

Переписка вернётся только из резервной копии и только та её часть, что в копию
попала: приватные ключи прежнего телефона не покидали его, и расшифровать
остальное нечем ни серверу, ни новому телефону. Отсюда практический вывод,
который стоит сказать всем заранее: **копию надо делать до потери телефона, а не
после**.

Если пароль тоже забыт — восстановления нет: почта не подтверждается, письмо
отправлять нечем, а «сброс пароля по просьбе в консоли» означал бы, что доступ к
аккаунту даёт доступ к серверу. Тогда остаётся регистрация нового аккаунта, а
прежний удаляется (§5).

## 4. Куда уходит место

```bash
docker compose exec server npm run status
df -h
du -sh data
```

`status` показывает размер файла базы, объём шифротекста по типам сообщений и
размер резервных копий по участникам. Что откуда берётся:

- **`media`, `voice`, `image`** — самое тяжёлое. Файл до 25 МБ превращается в
  пакет до ~45 МБ (base64 внутри base64), и всё это лежит в базе до доставки.
  Одна пересылка видео весит больше, чем вся переписка за месяц.
- **Резервные копии** — до 8 МБ на участника (`MAX_BACKUP_BYTES`), и они лежат
  постоянно, а не до доставки.
- **`messages` с давними датами** — сообщения тем, кто давно не заходил. Они
  ждут доставки до `MESSAGE_TTL_DAYS` (по умолчанию 14).

Сервер сам раз в час удаляет доставленные всем получателям, просроченные по TTL и
удалённые сообщения. Но **удаление строк не уменьшает файл базы**: страницы
остаются в свободном списке и переиспользуются. Строка «из них свободно после
удалений» в `status` показывает, сколько вернёт диску `VACUUM`:

```bash
docker compose down
docker compose run --rm server node -e "require('better-sqlite3')('/app/data/server.db').exec('VACUUM')"
docker compose up -d
```

`VACUUM` требует свободного места примерно в размер базы — при заполненном диске
он не сработает. Тогда сначала удали старые `backup-*.db`.

Если места мало постоянно, уменьши `MESSAGE_TTL_DAYS` в `.env` и перезапусти
(`docker compose up -d`). Это прямой компромисс: чем меньше TTL, тем выше шанс,
что человек, не заходивший неделю, не увидит адресованные ему сообщения вообще —
сервер удалит их раньше, чем он подключится.

## 5. Удалить участника

```bash
docker compose exec server node dist/cli/remove-user.js                       # список
docker compose exec server node dist/cli/remove-user.js --user=ad4e6bf9-...   # удалить
```

Id подставляется **без** угловых скобок: `<` оболочка воспримет как
перенаправление ввода.

Удаляются устройства, сообщения, квитанции, коды приглашений, связи контактов в
обе стороны и резервная копия. У остальных участников этот человек исчезнет из
списка сам при следующем подключении — вместе с перепиской с ним.

Перед удалением своего же старого аккаунта назначь главным текущий
(`set-admin.js --user=… --sole`, docs/DEPLOY.md §8a): иначе право уйдёт другому
человеку по времени регистрации.

## 6. Обновление сервера

```bash
cd family-messenger
git pull
docker compose up -d --build
```

Миграции применяются при запуске сами, `./data` не трогается. **Сними копию до
обновления** (§1): миграция меняет схему, и откат «git checkout прежней версии»
базу назад не приведёт.

После обновления:

```bash
docker compose logs --tail=50 server
docker compose exec server npm run status
```

В логах должно быть `[migrate] готово` и число применённых миграций.

Клиент и сервер обновляются раздельно, и это нормально: APK у людей отстаёт.
Незнакомый тип пакета сервер отклоняет с `UNKNOWN_TYPE`, не разрывая соединение,
а клиент показывает «сервер устарел — обновите его» там, где функция без него не
работает. Порядок правильный такой: **сначала сервер, потом APK**.

## 7. Когда «не работает»

Сначала посмотри, доходит ли клиент до сервера вообще:

```bash
curl -s https://chat.example.com/healthz          # {"status":"ok","connectedDevices":2}
docker compose logs --tail=100 server | grep -i "WS-соединение\|отказ"
```

| Симптом | Что смотреть |
| --- | --- |
| `/healthz` не отвечает | `docker compose ps`, `docker compose logs caddy` — чаще всего сертификат или DNS |
| `/healthz` отвечает, `connectedDevices: 0` | до сервера не доходят телефоны: сеть у них или неверный адрес в приложении |
| в логах «WS-соединение открыто», но сразу «отказ в аутентификации» | `REVOKED` — устройство отозвано; `UNKNOWN_DEVICE` — участника удалили, нужен новый вход |
| у одного человека всё, у другого ничего | это клиент, а не сервер: настройки → Диагностика → «Проверить отправку» на его телефоне |
| сообщения не приходят после сворачивания | «Работать в фоне» в настройках + Батарея → «Без ограничений» (ARCHITECTURE.md §12) |
| «Ждут отправки» больше нуля при `connected` | сервер не подтверждает приём — почти всегда на нём старая версия, обнови (§6) |

В логи попадают только метаданные — `chatId`, `msgId`, `userId`, размер блоба,
статусы. Содержимого сообщений там нет и быть не может: сервер его не видит.
Поэтому по логам можно понять, дошло ли сообщение, но не что в нём.

`LOG_LEVEL=debug` в `.env` добавляет подробностей на время разбора; на постоянку
не оставляй — логи растут и съедают тот же диск.
