# Expo HAS CHANGED

Read the exact versioned docs at https://docs.expo.dev/versions/v57.0.0/ before writing any code.

# Новые нативные модули — только через requireOptionalNativeModule

Обычный импорт пакета с нативной частью (`expo-application`,
`expo-local-authentication`, локальные модули из `modules/`) бросает исключение
**при загрузке модуля**, если нативной части в сборке нет. А сборка отстаёт от
JS-бандла постоянно: dev-client APK собран раньше, у людей на телефонах старый
релиз. Если такой импорт лежит на пути к `App.tsx`, приложение падает при
запуске целиком — до соединения с сервером. Со стороны это выглядит как
«сообщения не отправляются», и причину по этому симптому не найти.

Поэтому любой нативный модуль подключается так:

```ts
import { requireOptionalNativeModule } from "expo-modules-core";
const native = requireOptionalNativeModule<Api>("ExpoSomething"); // null, если нет
```

Уже сделано так: `src/util/buildInfo.ts`, `src/lock/biometrics.ts`,
`modules/keep-alive/index.ts`. UI при `null` должен показывать «нет в этой
сборке», а не делать вид, что функция работает.

# Ничто не должно задерживать соединение

`AppProvider` монтируется сразу после загрузки identity. Всё остальное —
настройки блокировки, разрешения на уведомления, служба переднего плана —
подключается уже при живом соединении. Ранний `return` в `App.tsx` до
`AppProvider` означает «приложение не подключается, пока это читается», а отказ
такого чтения — «не подключается никогда». На этом я обжигался дважды: диалогом
разрешений перед `ws.connect()` и чтением настроек блокировки из Keystore.
